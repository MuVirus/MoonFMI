# 实施记录：2026-11-24 · 规范后端改为 native

> 目标：让编辑器的语言服务器能在 native-only 的包（`src/backend/native`、
> `src/cli`、三个要加载 FMU 动态库的示例）里给出补全与跳转。起因是
> `examples/` 落地后，用户发现只有目标中立的 `examples/common` 有代码提示。

## 背景

`examples/` 交付后出现一个现象：在 `examples/common` 下写代码有补全，在
`examples/simulate-cs` 等目录下没有。

查下来根因是**模块的规范后端**，不是 `.mbti` 本身：

- `moon.mod` 的 `preferred_target` 是 `wasm`，这是模块级设置，决定 `.mbti`
  按哪个后端生成，也决定语言服务器按哪个后端分析；
- `moon info` 只为规范后端写 `pkg.generated.mbti`（`--target` 只能"检查"
  别的后端，不能改写），于是 native-only 包在 wasm 下**根本没有接口文件**；
- 这三个示例声明了 `supported_targets = "native"`，在 wasm 后端下连构建
  计划都失败（`Package ... does not support target backend 'wasm'`），
  语言服务器拿不到语义模型，补全自然消失。

工具链侧没有开关：VS Code 扩展（0.7.2026112001 与 0.7.2026112401）的
`contributes.commands` 只有安装工具链、取 LSP 编译器版本、重启 LSP、切换
多行字符串和三个 go-to-references，`contributes.configuration` 里也没有任何
target 设置；`moon lsp` 本身只接受 `--stdio/--socket/--port/--pipe`，没有
`--target`。官方文档里写的 "Select backend" 命令在当前扩展里并不存在。

对照实验：

```text
preferred_target = "wasm"
$ moon ide hover --loc examples/simulate-cs/main.mbt:28:4
Error: could not get package of loc examples/simulate-cs/main.mbt:28:4

preferred_target = "native"
$ moon ide hover --loc examples/simulate-cs/main.mbt:28:4
fn run_cs(instance : &@fmi.CsInstance, references : Array[UInt]) -> @sim.SimulationResult raise @fmi.SimulationError
```

## 决策

把 `moon.mod` 的 `preferred_target` 改为 `native`。理由：本项目首个可用路径
就是 native 导入器，wasm 规范后端让 native-only 包既拿不到接口文件，也让
它们的公开接口**不在 CI 的「接口未变化」检查范围内**——2026-11-02 的记录
已经把这条列为遗留风险（"`src/backend/native` 没有 `pkg.generated.mbti`……
改接口不会在 CI 里报警"）。改规范后端同时解决编辑器补全与接口检查覆盖
两个问题。

代价（实测）：

- 已跟踪的 6 个 `.mbti` 内容**一字未变**——目标中立包的 native 接口与
  wasm 接口相同；
- 新增 4 个接口文件：`cmd/main/`、`src/backend/native/`、`src/cli/`、
  `tests/integration/`（native-only 包在 wasm 规范下没有接口）；
- `examples/` 下三个 native-only 示例也第一次拿到接口文件；
- `moon run cmd/main` 不再需要显式 `--target native`；
- **失去一个镜像**：`src/backend/wasm/pkg.generated.mbti` 被删除，详见下节。

## 镜像损失：`src/backend/wasm` 没有接口文件

`src/backend/wasm` 是 wasm-only 包（`supported_targets = "wasm"`），而
`moon info` 只为**规范后端**写 `pkg.generated.mbti`。规范后端改成 native
之后，这个包就落在了规范后端之外：

```text
$ moon info -p MuVirus/fmi/src/backend/wasm
Warning: No selected package supports target backend `native` for `moon info`
Finished. moon: no work to do
$ Test-Path src/backend/wasm/pkg.generated.mbti
False
```

实测确认**没有任何命令会把它写回来**（文件删除后逐个验证）：

| 命令 | 是否生成 `src/backend/wasm/pkg.generated.mbti` |
| --- | --- |
| `moon info`（native 规范后端） | 否 |
| `moon check --target wasm` | 否 |
| `moon build --target wasm` | 否 |
| `moon test --target wasm` | 否 |

因此把该文件从版本控制里删除是**稳定**的：CI 的「拒绝脏工作区」步骤不会
因为 `moon check --target wasm` 把它写回来而失败。

代价是明确的：wasm 后端的公开接口不再被 CI 的「接口未变化」检查覆盖，
`src/backend/wasm` 的接口变更需要在提交说明里人工提示。它的实现目前只有
一个 `WasmBackend::new()` 占位（`src/backend/wasm/wasm.mbt`，20 行），
等到 LS-WASM 绑定真正落地、接口有了实际内容再决定是否要重新纳入跟踪。

未采用的替代方案：把 `src/backend/wasm` 改成目标中立。它能拿回接口文件，
但会削弱仓库既有的后端隔离约定，还要连带改 `tools/check-deps.mbtx` 的
`target_rules`——为 20 行占位代码不值得。

## 交付清单

1. `moon.mod`：`preferred_target` 由 `wasm` 改为 `native`；
2. `moon info` 重新生成接口，新增 4 个 `.mbti` 需要提交；
3. 删除 `src/backend/wasm/pkg.generated.mbti`（见「镜像损失」一节）；
4. 文档同步：`docs/design/architecture.md`（规范后端语义）、`docs/guides/quick-start.md`
   （常见坑）、`examples/README.md`（`--target native` 的说法）、
   `docs/research/moonbit-ecosystem.md`（补后记）、`docs/research/wasm-fmi.md`
   （动机表里的陈旧事实）；
5. `CHANGELOG.md` 的 `[Unreleased]` 记录这条用户可见变化。

wasm 仍是受支持的目标：`moon check --target wasm --deny-warn` 与
`moon test --target wasm --deny-warn` 照常通过，CI 闸门里的显式
`--target` 保持不变（显式写法不依赖规范后端的取值）。

## 验证

- `moon run scripts/check.mbtx --target native` → all checks passed（含
  `check: wasm`、`test: wasm`、`public interface`）；
- `moon test --target native --deny-warn` → 248 通过 / 0 失败；
- `moon ide hover --loc examples/simulate-cs/main.mbt:28:4` 不带 `--target`
  也能解析（改动前报 "could not get package of loc"）。

## 探查修正

- `moon info` 有缓存坑：切换 `preferred_target` 后 `_build` 里残留的旧后端
  产物会让它一次性给 native-only 包也生成 `.mbti`，与规范后端不一致。改
  规范后端前先 `moon clean` 再跑 `moon info`，接口集合才稳定。
- 排查过程中 `docs/roadmap/p0-plan.md` 与 `docs/roadmap/p0-report.md` 从工作
  区消失（HEAD 里有、磁盘上没有）。逐个验证 `moon info` / `moon fmt` /
  `moon check` 都不是元凶，已从 git 原样恢复（与 HEAD 无 diff）。
