# 2026-10-31

今天做的是 P0 第二周的三件小事：安全地读 `modelDescription.xml`、安全地打开 FMU 这个 ZIP 包、加载并卸载一个动态库。三件事都不追求功能完整，只要求能跑通、能在出错时给出说得清原因的信息，并且能挡住恶意输入。

先约定三个词。**动态库**是 Windows 的 `.dll` 或 Linux 的 `.so`，FMU 里的模型代码就放在这种文件里，程序运行时才把它加载进内存。**解压炸弹**指压缩包很小、解开后却极大，足以撑爆内存或磁盘。**路径穿越**指压缩包里的文件名写成 `../../某个系统文件`，如果解压时不检查，就会写到目标目录之外。

先给结论：XML 和 ZIP 两件已经按计划完成；动态库能加载、能调用、能卸载，四类失败都能诊断；只有一项指标没达到——1 MB 的说明书读完约 144 毫秒，目标是 100 毫秒。原因和后续处理写在最后一节。

## 1. 读 XML

### 1.1 为什么不自己写解析器

XML 解析看起来简单，真正麻烦的是命名空间、CDATA、字符引用、实体、编码和错误定位。这些细节一旦写错，错误往往出现在很远的后续逻辑里。

所以解析本身交给现成的 `Milky2018/xml`。它是 pull 模式（调用方每次取一个事件，而不是一次性建整棵树），native 和 WebAssembly 都能跑，每个事件都带源码位置。我们的代码在它外面包一层，只补它不管的四件事：

- 解析前检查文档大小，默认上限 32 MB；
- 出现 `<!DOCTYPE` 直接拒绝；
- 限制嵌套深度、属性个数、单个属性长度；
- 把它的位置信息统一成“行、列”。

### 1.2 对外接口

包 `src/xml` 暴露的东西不多：`XmlReader` 负责取事件，`XmlEvent` 是事件种类，`XmlError` 是错误，`XmlLimits` 是各项上限。`XmlEvent` 覆盖开始标签、结束标签、自闭合标签、文本、CDATA、注释、处理指令、XML 声明和文件结束。

`XmlError` 分四类，其中三类都带行号和列号：

| 错误 | 含义 | 带位置 |
| --- | --- | --- |
| `InvalidInput` | 输入不是合法 UTF-8 等前置问题 | 否 |
| `LimitExceeded` | 超过大小、深度、属性数量或属性长度上限 | 是 |
| `DoctypeNotAllowed` | 文档里出现 `<!DOCTYPE` | 是 |
| `ParseError` | 底层解析器报出的语法错误 | 是 |

拒绝 `DOCTYPE` 是刻意的。FMI 的说明书不需要 DTD，而“十亿笑声”（billion laughs，用层层嵌套的实体把几行文本膨胀成数 GB）正是靠 DTD 里的实体定义实现的。在创建解析器之前就扫一遍原文并拒绝，实体展开根本没有机会发生。这里还额外处理了一个细节：`DOCTYPE` 关键字大小写不敏感，`<!doctype` 也拦。

读取字节时用 `moonbitlang/x/encoding` 解码 UTF-8；非法字节直接返回 `InvalidInput`，不会进入解析器。

### 1.3 测试覆盖

`src/xml/xml_wbtest.mbt` 里有 13 个测试：

| 场景 | 期望 |
| --- | --- |
| 一份完整的 FMI 2 说明书 | 事件、属性、行号都正确 |
| 嵌套元素 | `depth()` 随开始/结束变化 |
| 中文元素名、属性和文本、CDATA | 原样读出 |
| 注释和处理指令 | 作为事件暴露 |
| 截断的文档 | `ParseError`，行列号大于 0 |
| 20 层嵌套、上限设为 4 | `LimitExceeded`，消息说明是深度 |

| 超过大小上限 | `LimitExceeded`，行列号为 1/1 |
| 十亿笑声 | `DoctypeNotAllowed`，定位到第 2 行第 1 列 |

## 2. 打开 ZIP

### 2.1 分工

ZIP 的目录解析和 deflate 解压交给 `hustcer/fzip`，安全策略全部由我们控制。这样分工的原因是：压缩算法自己写容易出错，而“哪些文件允许被解开”完全是我们自己的判断。

`src/zip` 的入口是 `ZipArchive::open`，它只读目录，不解压内容。因为安全检查必须在解压之前完成——如果先解开再检查，炸弹已经爆了。

`open` 按顺序做这些检查：

| 检查 | 默认上限 | 拒绝原因 |
| --- | --- | --- |
| 压缩包总大小 | 256 MB | `ArchiveTooLarge` |
| 条目数量 | 4096 | `TooManyEntries` |
| 单个条目解压后大小 | 64 MB | `EntryTooLarge` |
| 所有条目解压后总和 | 256 MB | `ArchiveTooLarge` |
| 单条压缩比 | 200 倍 | `CompressionRatioExceeded` |
| 压缩方法 | 只允许 0（存储）和 8（deflate） | `UnknownCompression` |
| 条目路径 | 见下 | `UnsafePath` |
| 重名条目（忽略大小写） | 不允许 | `DuplicateEntry` |

路径检查拒绝这些写法：绝对路径（以 `/` 开头）、盘符（`C:`）、反斜杠、`..` 和 `.` 组件、控制字符、空名称、超过 4096 字符的名称。反斜杠被直接禁止，因为 Windows 上它等价于目录分隔符，只在 Linux 上检查 `/` 会留下漏洞。重名检查忽略大小写，是因为在 Windows 和 macOS 上 `A.xml` 和 `a.xml` 会写到同一个文件。

### 2.2 校验和

`fzip` 在解压时能校验 CRC-32（ZIP 每条目自带的校验值），但报错时只说“校验失败”，不说是哪一条。

只报“校验失败”对使用 FMU 的人没有帮助，所以 `src/zip` 自己又读了一遍 ZIP 的中央目录，把每条目记录的 CRC 取出来，逐条比对。这样错误信息能写成 `ZIP entry 'binaries/win64/x.dll' failed its CRC-32 check`。如果遇到 ZIP64（超大压缩包用的扩展格式）或结构不符合预期，就退回让 `fzip` 自己校验，不会因为我们的附加检查而拒绝正常文件。

### 2.3 解压到哪里

这一版不写磁盘：`extract_all` 把内容解到内存里返回。这样一来，“解压失败后临时目录有残留”这个问题根本不存在。真正落盘要到第三周，届时再按设计文档用私有临时目录并在失败时清理。

### 2.4 测试覆盖

`src/zip/zip_wbtest.mbt` 里有 11 个测试，其中 8 个是故意构造的坏压缩包：

| 场景 | 期望 |
| --- | --- |
| 两个正常条目 | 能列出、能读、内容正确 |
| 目录条目（以 `/` 结尾） | 被标记为目录 |
| `../evil.dll` | `UnsafePath`，错误里带条目名和原因 |
| 绝对路径、反斜杠路径 | `UnsafePath` |
| `ModelDescription.xml` 与 `modeldescription.xml` 并存 | `DuplicateEntry` |
| 1 MB 的零字节条目 | `EntryTooLarge` 或 `CompressionRatioExceeded` |
| 两个条目总和超过总额 | `ArchiveTooLarge` |
| 条目数超过上限 | `TooManyEntries` |
| 截断压缩包 | `Truncated` 或 `InvalidArchive` |
| 改坏第一条的 CRC | `ChecksumMismatch`，指名 `good.txt` |
| 没有条目的压缩包 | 条目数为 0，解压结果为空 |

`tests/integration` 是只在 native 上运行的集成测试包，直接读 `tests/data/.cache` 里的真实 FMU。

选 5 个样品（3 个 FMI 2、2 个 FMI 3）做端到端检查：

- `modelDescription.xml` 能被 `XmlReader` 完整读出，根元素是 `fmiModelDescription`，`fmiVersion` 与清单一致，`modelName` 非空；
- 把 FMU 截断到 4 KB 后，`ZipArchive::open` 拒绝它。

这些测试跑之前需要先取语料：

```bash
node tests/data/fetch-fmus.mjs
```

有两点需要说明清楚，避免把“没做”当成“做了”：

- 验收标准里写的是“解压结果与 `7z x` 逐文件一致”，但这台机器上没有 7z，所以没有做逐字节对比。实际做的是：条目清单与 `tests/data/manifest.json` 的路径一致、大小一致、CRC 校验通过。逐文件对比要等 CI 里装上 7z 再补。
- `fzip` 不暴露 ZIP 的“外部属性”字段，所以符号链接条目无法被识别。当前的兜底是：这一版不落盘，符号链接没有危害；第三周落盘前必须补上对符号链接的检查。

## 4. 加载动态库

### 4.1 为什么中间隔一层 C

Windows 用 `LoadLibraryExW` / `GetProcAddress` / `FreeLibrary`，Linux 用 `dlopen` / `dlsym` / `dlclose`。MoonBit 的 FFI 能直接声明 C 函数，但这两套 API 的参数类型不一样：Windows 的路径是 UTF-16，Linux 是字节串；错误信息一个来自 `GetLastError`，一个来自 `dlerror`。

所以加了一个很小的 C 文件 `src/backend/native/dl.c`，用 `native-stub` 配置让 MoonBit 的 native 构建顺手把它编进去。MoonBit 侧只面对三个统一的函数名，平台差异都留在 C 里。

Windows 上路径要先从 UTF-8 转成 UTF-16 再调 `LoadLibraryExW`，并且用 `LOAD_WITH_ALTERED_SEARCH_PATH`，让同目录的依赖库能被找到——FMU 的 `.dll` 常常依赖同目录下的其他库。错误信息用 `FormatMessageW` 取系统原文，再转回 UTF-8。

### 4.2 MoonBit 侧的行为

`DynamicLibrary::open` 先检查文件是否存在，不存在直接返回 `LibraryNotFound`，不必依赖系统错误码去猜。加载失败时区分两种：

- `MissingDependency`：库本身存在，但它依赖的库不在；
- `LoadFailed`：其他原因。

`symbol` 找不到函数时报 `SymbolNotFound`，消息里有库路径、函数名和系统原文。卸载后再取函数会明确报“库已卸载”，不会去碰野指针。

判断“缺依赖”不能只靠错误文本。Windows 中文版的 `FormatMessageW` 返回的是“找不到指定的模块。”，里面没有 `126`，按英文关键字匹配会漏判。所以 C 侧额外提供了一个读 `GetLastError()` 的接口，Windows 上按错误码 `126`（`ERROR_MOD_NOT_FOUND`）判断。这里还有个顺序问题：格式化错误信息本身会重置线程的最后错误码，所以必须先读码、再取文本。

### 4.3 测试用的动态库

`tests/abi/fixture.c` 导出四个函数：

| 函数 | 作用 |
| --- | --- |
| `moonfmi_add(int, int)` | 整数加法 |
| `moonfmi_multiply(double, double)` | 浮点乘法 |
| `moonfmi_fill_point(struct*, double, double)` | 往结构体里填两个字段 |
| `moonfmi_invoke(callback, int)` | 接收回调 |

`tests/abi/broken.c` 故意依赖 `tests/abi/dependency.c` 里的函数，编译完再把被依赖的库删掉，用来制造“库存在但缺依赖”的场景。

构建脚本是 `tests/abi/build-fixture.ps1` 和 `build-fixture.sh`，产物放在 `tests/abi/.cache/`（已忽略，不进 git）。检查脚本会在跑测试前先构建一次。

### 4.4 实测结果

| 场景 | 结果 |
| --- | --- |
| 加载正常库并调用整数、浮点函数 | 结果正确 |
| 往结构体里填两个 `double` | 内存布局正确 |
| 加载不存在的文件 | `LibraryNotFound` |
| 加载存在但缺依赖的库 | `MissingDependency`，消息含库路径 |
| 取不存在的函数 | `SymbolNotFound`，消息含库路径和函数名 |
| 卸载后再取函数 | `SymbolNotFound`，消息说明已卸载 |
| 卸载后删除库文件 | 删除成功 |

最后一条是 Windows 上最值得测的：文件被加载后会被锁定，卸载必须真正释放引用，文件才删得掉。测试里先复制一份库、加载、卸载、删除，删除失败即视为卸载没有真正完成。

回调那条测试目前只验证了“函数能被调用”，没有验证“C 反过来调用 MoonBit 的回调”。原因是 `FuncRef` 跨语言传回调还需要确认参数传递约定，这属于第三周 C 中间层的范围，不在这次实验里。

## 5. 没达标的一项

验收标准里写着“1 MB 的说明书在开发机上 100 毫秒内读完”。实测没有达到。

用一份 1.08 MB、约 11000 个 `ScalarVariable` 的合成文档测量（结构与真实说明书相同，平均每个事件约 24 字节，和真实样品一致），release 构建下连跑 5 次取最好成绩：

```text
XmlReader::new      4 ms
read_events       144 ms
合计              153 ms
```

换成 250 毫秒作为自动检查的阈值，同时把它登记为风险。这个数字本身还有两个细节：

- 我们的封装只占 4 毫秒（大小检查加 `DOCTYPE` 扫描），剩下的都在第三方解析器里；
- 同一份文件 raw（不经过封装）直接调用 `Milky2018/xml` 是 149 毫秒，差别在测量噪声范围内。

也就是说，瓶颈不在这一层封装，而在解析器本身，约合 7 MB/s。真实样品很小（最大 4.9 KB），感觉不到；大模型（上万个变量）才会碰到。

可能的处理方向，留给 P1 决定：

1. 先接受现状。7 MB/s 对几十 KB 的说明书完全够用，只有上万个变量的模型才需要等约 0.2 秒。
2. 只解析需要的部分，跳过注释、文本节点等用不上的事件，减少对象分配。
3. 换解析器，或写一个只覆盖 FMI 说明书子集的专用解析器。这条路成本高，但如果 P1 的性能目标更严，可能免不了。

自动检查里保留了性能测试，debug 构建放宽到 1 秒（debug 大约慢一倍），release 构建 250 毫秒。这样能拦住明显的性能退化，又不会让正常开发被误报卡住。

## 6. 其他遇到的问题

- `moon.pkg` 里同一路径不能用两个别名导入，否则整包报“找不到包”。测试文件和被测代码分属不同的导入作用域，测试文件的依赖要写在 `for "test"` 里。
- MoonBit 没有 `Int::max_value`，用具体数值代替。
- `Bytes::to_string` 不是按 UTF-8 解码，直接用它比较内容会得到乱码；读文本要显式调用 `@utf8.decode`。
- `fzip` 的 `unzip_list` 不返回 CRC，所以校验和归因要自己再读一遍中央目录。
- 平台相关的错误文本会随系统语言变化，不能拿英文关键字做判断，必须用错误码。
