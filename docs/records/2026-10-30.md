# 2026-10-30

今天完成的是 MoonFMI 的工程基础设施，不涉及具体功能。内容包括：把代码拆成 9 个包、加一套依赖方向检查、配置 Windows 和 Linux 的自动检查、准备 8 个真实 FMU 作为测试样品，以及用官方 XSD 做外部对照。

先说明两个后面会反复出现的词。FMU（Functional Mock-up Unit）是 FMI 标准规定的模型打包文件，本质上是一个 ZIP 包，里面至少包含模型描述文件 `modelDescription.xml`，通常还包含平台相关的动态库。XSD 是 XML 的语法规则文件，用来描述元素顺序、必填属性和合法取值。

这样做的目的，是让后续的 XML 解析、ZIP 解包、动态库加载和 WebAssembly（一种可在浏览器里执行的字节码格式）实验有一个能编译、能测试、能发现错误的起点。

## 1. 代码框架

### 1.1 九个包

按交付物把代码拆成 9 个包，每个包先放一个占位类型和一个白盒测试（测试代码和被测代码在同一个包里）：

| 包 | 职责 | 依赖 |
| --- | --- | --- |
| `src/zip` | ZIP 容器与安全解压 | 无 |
| `src/xml` | XML 读取与安全限制 | 无 |
| `src/schema` | FMI 2/3 类型化模型与语义校验 | `xml` |
| `src/fmi` | 打开 FMU、实例与后端抽象 | `schema`、`zip` |
| `src/backend/native` | 本机动态库后端 | `fmi` |
| `src/backend/wasm` | WebAssembly 后端 | `fmi` |
| `src/sim` | 联合仿真主算法 | `fmi` |
| `src/export` | 导出流程与打包 | `schema`、`zip` |
| `src/cli` | 命令行入口（把各包组合起来） | `export`、`sim` |

`backend/native` 和 `backend/wasm` 分别只在 native（编译成本机机器码）和 WebAssembly（浏览器沙箱）目标下参与编译；其余 7 个包保持平台无关。这里的“后端”指真正加载并调用 FMU 的那一层。这样上层的主算法不需要知道底层用的是哪种后端，两个后端之间也不会互相依赖。

9 个包每包一个测试；每个目标只编译 7 个平台无关包加上自己的后端，所以每个目标实际运行 8 个测试：

```text
Total tests: 8, passed: 8, failed: 0.
```

在 MoonBit 上遇到两个需要记录的问题：

- 枚举变体默认在包外只读，跨包构造要使用 `pub(all) enum`；
- 派生 `Eq` 和 `Debug` 在 `--deny-warn` 下会提示隐式方法提升，需要显式写 `pub extend ...`，并导入 `moonbitlang/core/debug`。

### 1.2 依赖方向检查

新增 `tools/check-deps.mjs`。它读取每个包的 `moon.pkg`，对照架构文档里的分层表，发现“下层反过来依赖上层”就报错。允许的方向是：

```text
zip、xml                     不依赖其他包
schema                       依赖 xml
fmi                          依赖 schema、zip
backend/native、backend/wasm 依赖 fmi
sim                          依赖 fmi
export                       依赖 schema、zip
cli                          依赖其余全部
```

除了反向依赖，脚本还检查两个后端的 `supported_targets` 是否正确，以及核心包有没有误设目标限制。

检查器带一个自检模式，会故意构造一条反向依赖，确认自己真的能报错：

```text
$ node tools/check-deps.mjs --self-test
dependency checker self-test passed
```

另外也做了一次真实测试：在 `src/zip/moon.pkg` 里临时加入对 `src/schema` 的导入，检查器按预期报出 `src/zip imports src/schema` 并返回失败。

### 1.3 自动检查

新增 `.github/workflows/ci.yml`，在 Ubuntu 和 Windows 上各跑一遍。MoonBit 版本固定为 `0.1.20261023`，避免“今天能过、明天因为工具链升级突然失败”。

| 检查 | 目的 |
| --- | --- |
| 依赖方向 | 防止分层被破坏 |
| 格式 | 保证代码风格一致 |
| 编译 native / wasm | 两个目标都能通过 |
| 测试 native / wasm | 行为符合预期 |
| 公开接口 | 生成文件与源码一致 |
| XSD 对照 | 用官方规则检查测试样品 |

本地入口有两个，步骤与 CI 保持一致：

- `scripts/check.sh`：Linux、WSL、Git-Bash；
- `scripts/check.ps1`：Windows PowerShell。

接口检查有一个细节需要说明。`moon check` 本身也会更新 `pkg.generated.mbti`，如果只在最后比较文件，手改或过期的接口会被自动修好，检查就失去意义。所以脚本在开始时先记录所有 `.mbti` 的哈希，然后删除文件、重新执行 `moon info`，再和开头的哈希对比。这样无论是手改接口，还是改了源码却忘了重新生成，都会被发现。

新增 `.gitattributes`，统一使用 LF 换行。否则 Windows 的换行转换和 `moon fmt` 的输出会互相冲突，格式检查容易出现假失败。

### 1.4 公开接口

`moon info` 为各包生成 `pkg.generated.mbti`。`.mbti` 是 MoonBit 自动生成的公开接口摘要，记录其他包能看到哪些类型和函数。`backend/native` 没有生成，是因为模块默认目标是 WebAssembly，接口文件只按默认目标生成；这是工具链的预期行为。

## 2. 真实 FMU 测试样品

选择 Reference-FMUs 作为第一批测试文件，版本 `v0.0.42`，许可证为 BSD-2-Clause。Reference-FMUs 的发布压缩包约 4.4 MB，SHA-256 为 `b6b4a195b9c0f6bdd3459cd949cbb35fc21ee2049d6dab4cb7a3ba7da63b1e97`。

FMU 文件不放进 git：单个文件有几 MB，而且各自带许可证。仓库里只保存清单 `tests/data/manifest.json` 和下载校验脚本，文件缓存到 `tests/data/.cache/`，该目录已被忽略。

清单里收录了 8 个样品。表中的 ME 是 Model Exchange（模型交换），CS 是 Co-Simulation（联合仿真），它们是 FMI 定义的两种接口类型：ME 把模型方程交给外部求解器，CS 则由 FMU 自己负责推进时间。

| 样品 | FMI 版本 | 接口 | 覆盖点 | 大小 |
| --- | --- | --- | --- | --- |
| `fmi2-bouncingball` | 2.0 | ME、CS | 输出、事件指示器 | 218,148 |
| `fmi2-feedthrough` | 2.0 | ME、CS | 6 输入 / 6 输出、直通 | 218,651 |
| `fmi2-resource` | 2.0 | ME、CS | `resources/` 目录 | 217,421 |
| `fmi2-dahlquist` | 2.0 | ME、CS | 状态、参考轨迹 | 206,357 |
| `fmi3-bouncingball` | 3.0 | ME、CS | 输出、事件 | 363,815 |
| `fmi3-feedthrough` | 3.0 | ME、CS | 双向传值 | 371,241 |
| `fmi3-resource` | 3.0 | ME、CS | `resources/` 目录 | 405,537 |
| `fmi3-statespace` | 3.0 | ME、CS | 数组、状态 | 363,594 |

FMI 2 和 FMI 3 的动态库目录不同，清单里已经按样品记录了实际路径：

| 标准 | Windows x64 | Linux x64 |
| --- | --- | --- |
| FMI 2 | `binaries/win64/<id>.dll` | `binaries/linux64/<id>.so` |
| FMI 3 | `binaries/x86_64-windows/<id>.dll` | `binaries/x86_64-linux/<id>.so` |

8 个样品都确认包含 Windows x64、Linux x64 和 `modelDescription.xml`，其中 2 个包含 `resources/`。

下载与校验脚本 `tests/data/fetch-fmus.mjs` 支持四种用法：

| 用法 | 行为 |
| --- | --- |
| 直接运行 | 缺什么取什么，然后全量校验 |
| `--offline` | 只校验缓存，不下载 |
| `--force` | 清空缓存后重新下载 |
| `--list` | 打印样品 id、版本和接口 |

脚本先校验缓存文件的大小和 SHA-256；全部正确就直接结束，否则从缓存的发布压缩包重新解压；压缩包也无效时才联网下载。因此断网时只要缓存完整，仍然可以跑测试。

验证时做了两次破坏：

- 改一个字节但保持长度不变，脚本报告 SHA-256 不匹配；
- 增加一个字节，脚本报告大小不匹配。

恢复后运行 `--offline`，8 个文件全部通过校验。

## 3. 官方 XSD 对照

前面说过，XSD 是 FMI 官方提供的 XML 语法规则，规定元素顺序、必填属性和合法取值。本次没有实现 XSD 引擎，也没有把它接进 MoonBit 代码；XSD 只作为外部对照工具，用来判断问题出在解析器还是测试样品本身。

本机没有 Python 和 `xmllint`，因此使用 PowerShell 和 .NET 的 `System.Xml.Schema`。Windows 调用 `powershell`，Linux 和 CI 调用 `pwsh`。

安全设置：

- 实例文档禁止 DTD；
- 禁止外部实体；
- 不联网；
- 文档大小上限 32 MB；
- 允许 XSD 解析仓库内的相对 `xs:include`。

5 个样品的预期和结果：

| 样品 | 类别 | 预期 | 是否符合预期 |
| --- | --- | --- | --- |
| `fmi2-valid` | 完全合法 | 通过 | ✅ 符合 |
| `fmi3-valid` | 完全合法 | 通过 | ✅ 符合 |
| `fmi2-missing-guid` | 结构错误（缺必填） | 失败 | ✅ 符合 |
| `fmi2-unknown-index` | 结构合法但语义错误 | 通过 | ✅ 符合 |
| `fmi2-external-entity` | 外部实体 | 失败 | ✅ 符合 |

其中 `fmi2-unknown-index` 最能说明边界：`<Unknown index="99">` 指向一个不存在的变量，XSD 仍然判定通过。这说明 XSD 只能保证语法正确，变量引用是否有效必须由单独的语义校验处理。

目前还缺“超大文件”“元素顺序错误”“枚举值非法”三个样品，后续补充。
