# 2026-11-02

今天做的是 P0 第三周：把 C 代码真正编进 MoonBit 的构建，接住 FMU 打出的日志，把 C 侧的类型尺寸固化成基准，然后用一个独立的 C 宿主和一个 MoonBit 后端跑同一个真实模型。

先给结论：四件事都做完了。C 中间层用配置里的 `native-stub` 直接编进包，Windows 和 Linux 都不需要额外的编译或链接参数；日志的长度、编码、内存、生命周期都有测试；ABI 基准已在两个平台生成并接入自动检查；BouncingBall 这个 FMI 2 CS 模型在 C 宿主和 MoonBit 里各跑 300 步，六个采样点逐点一致。只有一处和原计划不同：日志的可变参数没有做格式化，原因写在 §3.4。

---

## 1. 把 C 编进构建

按计划里的顺序，先试最干净的一条：在 `src/backend/native/moon.pkg` 里写

```text
supported_targets = "native"

options(
  "native-stub": [ "dl.c", "fmi2_shim.c" ],
)
```

`moon build` 和 `moon test` 会把这些 C 文件交给工具链自带的编译器（Windows 上是 MSVC `cl.exe`，Linux 上是系统 `cc`），产物直接进最终可执行文件。第一条路一次就通了，所以“先编静态库”和“单独编动态库”两条退路没有实际尝试。

顺带确认了几件容易出问题的事：

- 头文件用相对路径就能包含，不需要 `-I`。shim 里写 `#include "../../../docs/standards/headers/fmi2/fmi2Functions.h"`，`tests/abi` 里的 C 文件深一层，写 `../../docs/...`。官方头文件只有一份，不复制、不重写。
- 运行库不需要手工对齐。以前担心的 MSVC `/MD` 和 `/MT` 混用问题，在“同一个构建、同一个编译器”的前提下不存在。只有改用预编译静态库时才会重新出现。
- 不需要 `cc-link-flags`，也没有符号冲突。shim 导出的函数统一带 `moonfmi_` 前缀。

这条结论写回了 [`../design/ffi-and-abi.md`](../design/ffi-and-abi.md) §8.1，包括失败时该退到哪一步。

> 这里要区分两个“C 编译器”：`native-stub` 用的是工具链自己的 MSVC；`tests/abi` 下的测试样品和参考宿主是让 LLVM clang 编的。两者互不影响，因为测试样品是运行时加载的动态库，不参与 MoonBit 的链接。

## 2. 中间层做什么

`src/backend/native/fmi2_shim.c` 是唯一直接面对 FMI 2 头文件的地方。MoonBit 侧看不到 `fmi2Component`，也看不到任何结构体。

### 2.1 加载与校验

打开库时解析 11 个 CS 必需的符号：`fmi2GetTypesPlatform`、`fmi2GetVersion`、`fmi2Instantiate`、`fmi2FreeInstance`、`fmi2SetupExperiment`、`fmi2EnterInitializationMode`、`fmi2ExitInitializationMode`、`fmi2Terminate`、`fmi2DoStep`、`fmi2GetReal`、`fmi2SetReal`。缺任何一个就拒绝，并指出缺的是哪个。

解析成功后还要问一次 `fmi2GetTypesPlatform()`。只接受 `"default"`，因为其他类型平台意味着 `fmi2Real`、`fmi2ValueReference` 的宽度可能和我们的假设不同。这一步在第二周只是设计里的一句话，现在是代码里的硬检查。

错误文本放在线程局部缓冲区里，MoonBit 调用失败时再取出来解码。这样不需要在 C 和 MoonBit 之间传可变长度的错误对象。

### 2.2 编译期断言

只保留四条，覆盖 CS 路径上最容易错位的四件事：

```c
typedef char moonfmi_assert_boolean_is_int[sizeof(fmi2Boolean) == 4 ? 1 : -1];
typedef char moonfmi_assert_value_reference_is_int[
  sizeof(fmi2ValueReference) == 4 ? 1 : -1];
typedef char moonfmi_assert_real_is_double[sizeof(fmi2Real) == 8 ? 1 : -1];
typedef char moonfmi_assert_logger_is_first[
  offsetof(fmi2CallbackFunctions, logger) == 0 ? 1 : -1];
```

用负长度数组而不是 `_Static_assert`，是因为后者的可用性取决于 MSVC 的 `/std:` 版本，而数组长度为负在所有 C 编译器上都是硬错误。

### 2.3 资源路径

BouncingBall 第一次实例化失败，日志只有一句 “Failed to convert fmuResourceLocation to a file path.”。原因是 FMI 2 的 `fmuResourceLocation` 要的是 URI，不是文件路径。

处理放在 MoonBit 侧：`fmi2_resource_location` 把反斜杠换成斜杠，Windows 盘符前补 `file:///`，POSIX 绝对路径前补 `file://`，已经以 `file:` 开头的原样通过，最后保证以 `/` 结尾。这样调用方仍然传普通目录，不需要知道 URI 规则。

### 2.4 句柄与释放

C 侧的库对象持有动态库句柄、函数指针和一份“退休实例”链表。实例释放分三步：

1. MoonBit 先把日志接收端标记为关闭，`on_log` 从此不会再被调用；
2. shim 调 `fmi2FreeInstance`，释放闭包引用，把实例标成 `freed`；
3. 实例上下文不立即释放，而是挂到库的退休链表，等库卸载时统一释放。

第三步看起来浪费一点内存，但它挡住的是“FMU 在 `fmi2FreeInstance` 返回后仍然从别的线程打日志”这种不规范行为。假 FMU 就是故意在 `fmi2FreeInstance` 里打一条日志来测这个顺序。

库在有实例存活时拒绝卸载，错误是 `Fmi2InstancesAlive`。卸载之后再用实例会得到明确的“已释放”，而不是野指针。

## 3. 日志

### 3.1 截断

消息在 C 侧截到 4096 字节。截断点如果落在 UTF-8 字符中间，会向前退到字符边界：

```c
length = MOONFMI_FMI2_LOG_LIMIT;
while (length > 0 && ((unsigned char)text[length] & 0xC0) == 0x80) {
  length--;
}
```

判断依据是“这个字节是不是后续字节”（高两位是 `10`）。退到边界后，解码端永远看不到半个字符，也就不需要 `U+FFFD` 兜底。

假 FMU 覆盖了四种边界：8192 字节 ASCII、4094 字节后接 3 字节汉字、4093 字节后接 4 字节 emoji、正好 4096 字节。前两个退让，第三个不截断。测试同时断言结果里没有替换字符。

### 3.2 中文和 emoji

`中文🙂 你好，世界 — Ünïcode` 从 C 进去、从 MoonBit 出来，字节数一致、内容一致。这一条比看起来重要：MoonBit 的 `String` 是 UTF-16，`Bytes` 是字节，两者之间的转换只要有一处用错 API 就会变成乱码。

### 3.3 内存：一次实测推翻的假设

最初认为“把 `Bytes` 传进 MoonBit 闭包，所有权就转移给 MoonBit 了”。测试结果很直接：5 万条 4 KB 日志之后，常驻内存涨了 225 MB，正好是 5 万 × 4 KB 再乘上每条消息的三个字节数组。

原因写在 MoonBit 的 native ABI 里：**C 调用 MoonBit 函数时，参数是借用的，不是移交的**。被调用方不会替调用方减引用。所以 shim 必须自己收回：

```c
instance->log_thunk(instance->log_closure, (int32_t)status, name, kind, text);
moonbit_decref(name);
moonbit_decref(kind);
moonbit_decref(text);
```

补上三行之后，同一测试的增长回到噪声范围。

这个测试本身也改过两轮。第一版用 100 条 × 1000 步的短消息，阈值 8 MB，结果被分配器噪声顶到 9.6 MB。改成 4 KB × 5 万条后，真实泄漏是 200 MB 量级，噪声不会误报。另外 Windows 的堆和 glibc 都会保留已释放的块，所以在两次读数前分别调用 `_heapmin()` / `malloc_trim(0)`，让数字反映存活数据而不是峰值。

### 3.4 没有做的那一项：可变参数格式化

FMI 2 的日志函数是可变参数的，标准允许 `message` 按 `printf` 格式带参数。当前实现直接使用 `message` 原文，忽略 `...`。

这是一个有意的取舍。对任意 FMU 传来的格式串调用 `vsnprintf`，等于把对方的格式错误（`%s` 配错类型、`%n`、参数个数不对）变成宿主的未定义行为。真实 FMU 基本只传普通字符串，所以先不做；如果以后遇到确实依赖格式化的 FMU，再按白名单处理，而不是无条件转发。

这一点登记进了 [`../design/ffi-and-abi.md`](../design/ffi-and-abi.md) §4.1，不算“已完成”。

### 3.5 线程与迟到回调

假 FMU 会创建一个线程，从那个线程打一条日志，然后等它结束。测试通过，说明“FMU 自有线程回调 MoonBit”不会立刻崩。

没有验证的是“多个线程同时回调同一个实例”。当前实现没有队列也没有锁，消息在 FMU 调用的线程上同步投递，前提是同一实例同一时刻只有一个线程在回调。这个假设和它的边界写在 §4.3。

迟到回调的测试更直接：假 FMU 在 `fmi2FreeInstance` 里再打一条。MoonBit 侧收到的消息数在 `free()` 前后不变，说明关闭顺序有效。

### 3.6 测试清单

`tests/integration/fmi2_log_wbtest.mbt` 里 6 个测试：

| 场景 | 期望 |
| --- | --- |
| 初始化、步进、释放时的日志 | 前两类收到，释放中的那条被丢弃 |
| 中文 + emoji | 内容与字节数都不变 |
| 8 KB ASCII | 截到 4096 字节 |
| 两种字符边界 + 正好 4096 | 边界前退、正好时不截断、无替换字符 |
| FMU 线程日志 | 收到，类别正确 |
| 5 万条 4 KB 日志 | 常驻内存增长低于 48 MB |

## 4. ABI 基准

`tests/abi/probe.c` 只做一件事：用官方头文件打印 FMI 2 和 FMI 3 的尺寸、回调结构体字段偏移和枚举值，输出 JSON。它不定义任何结构体，头文件改了输出就跟着改。

两个平台各生成一份基准：

| 文件 | 环境 |
| --- | --- |
| `baselines/x86_64-windows.json` | Windows x86_64，MSVC 头文件与编译器 |
| `baselines/x86_64-linux.json` | Linux x86_64（WSL Ubuntu 22.04），clang |

两份内容目前完全相同，包括最值得对照的一对：FMI 2 的 `fmi2Boolean` 是 4 字节，FMI 3 的 `fmi3Boolean` 是 1 字节。`fmi2CallbackFunctions` 是 40 字节，`logger` 在偏移 0，`componentEnvironment` 在偏移 32。

两份分开保存而不是合成一份，是因为它们记录的是“这个平台实际是什么”，不是“我们认为它们应该相同”。哪天某个平台真的变了，要看见的是那一份的差异。

`tests/abi/check-abi.mjs` 先用 `--header` 问出本机对应的文件名，再逐字段比较。缺失、多出、值不同都会打印成 `fmi2.sizeof.fmi2Boolean: expected 4, got 8` 这样的行，而不是只报一句“不匹配”。

FMI 3 的 shim 这周没做，但尺寸基线已经覆盖 FMI 3 的类型。等到写 shim 时，至少不用再猜宽度。

## 5. C 参考宿主

`tests/abi/fmi2_host.c` 是一个独立的 C 程序，只依赖官方头文件和平台加载器。它加载 BouncingBall 的动态库，走完“实例化 → 初始化 → 300 次 10 ms 步进 → 终止 → 释放”，每 0.5 秒采样一次 `(time, h, v)`，输出 JSON。

第一次跑出来的只有最终状态，能说明“跑完了”，但不能说明“中间每一步都对”。改成六个采样点之后，轨迹上的每次弹跳都被覆盖：

| 时间 (s) | h | v |
| --- | --- | --- |
| 0.5 | 0.13560068699999941 | 2.64968099999999 |
| 1.0 | 0.23664368699999475 | -2.2553190000000161 |
| 1.5 | 0.07350171929999888 | -1.8420237000000108 |
| 2.0 | 0.054889077789000158 | -0.35254491299999868 |
| 2.5 | 0.00080600419771164038 | 0.17697604942791004 |
| 3.0 | 2.2250738585072014e-308 | 0.0 |

最后一行那个 `2.2250738585072014e-308` 不是错误，它正好是 double 的最小正规数：FMU 在触地后把高度限制到了这个值。保留原值而不做四舍五入，是为了让对照能发现任何一位的偏差。

`run-fmi2-host.ps1` / `.sh` 负责从 `tests/data/.cache` 里解出动态库、把资源目录转成 `file:` URI、跑宿主、写 JSON；`check-host.mjs` 用相对误差 1e-9 和基准比较。Windows 和 WSL 都跑过，结果一致。

## 6. MoonBit 跑同一个模型

`tests/integration/fmi2_wbtest.mbt` 用 `@zip` 解开同一个 FMU，取出当前平台的动态库，`Fmi2Library::open` 加载，然后按和 C 宿主完全相同的参数走一遍。

对照用的是同一份六点基准。时间容差 1e-9，变量容差 1e-12。时间容差更宽，是因为每个宿主都自己反复做 `time += 0.01`，300 次之后两条路径的舍入可能不同；`h` 和 `v` 直接来自 FMU 内部状态，两边喂进去的步长相同，可以卡得更紧。

结果全部一致。这一步的意义不只是“能跑”：C 宿主和 MoonBit 后端是两条互相独立的路径，前者完全不经过我们的 shim。两边对得上，才说明 shim 没有读错偏移、没有把 `size_t` 传错宽度、没有在 `fmi2GetReal` 的数组上搞错方向。

测试里也验证了库的状态：`version()` 返回 `"2.0"`，实例释放后 `is_freed()` 为真，库关闭后 `is_closed()` 为真。

## 8. 还没做的

- FMI 3 的 C shim：这周只做了 FMI 2 CS，FMI 3 的尺寸基线已经就位；
- Model Exchange：`fmi2SetTime`、`fmi2GetContinuousStates` 等尚未接入；
- 日志的可变参数格式化（见 §3.4），以及多线程同时回调同一实例的保证；
- 32 位、macOS、aarch64 的 ABI 基准；
- 用 FMPy 跑同一模型做第三方对照；
- 用 `7z x` 做 FMU 逐文件解压对比（第二周遗留）；
- `src/backend/native` 这个只在 native 上存在的包没有 `pkg.generated.mbti`：`moon info` 以 wasm 为规范后端，看到 native-only 包时只把差异打到标准输出，不落盘。因此它的公开接口目前不在“接口未变化”检查范围内，改接口不会在 CI 里报警；
- XML 1 MB / 100 ms 的性能目标仍未达到（第二周遗留，约 144 ms），已登记为风险；
- Windows/Linux CI 还没有在 GitHub 上实际跑过，本地检查脚本已通过。
