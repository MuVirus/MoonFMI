# 实施记录：2026-11-27 · 0.9（1.0 里程碑的内容：MoonBit 1.0 + moonfig 0.2.5）

> 目标：把 `MuVirus/fmi` 推到 **1.0 里程碑的内容**（roadmap 发布节奏表写的是"硬化、文档、交叉检查达标"），工具链基线升到 **MoonBit 1.0**，配置层依赖升到 **moonfig 0.2.5**，然后提交、推送、盯 CI，绿了才 `moon publish`。

## 背景

两件事凑到了一起：

- 上游 moonfig 在 2026-11-27 发布了 0.2.5，内容是"把 CI 锁到 MoonBit 1.0 发布候选版并在 README 写明 1.0 要求"——**库接口相对 0.2.4 未变**（两笔提交：一笔锁工具链 + 改 README，一笔抬版本号）。
- 本仓库的 CI 注释还写着"工具链无法固定版本"（2026-11-16 的记录）：当时上游只发布 `latest`，所有带版本的路径都返回 403。这条已经过期了——上游现在发布带版本号的构件，两个安装脚本都接受版本参数。

所以 1.0 这一版同时做两件事：把本仓库的工具链基线也锁到 MoonBit 1.0，并把 moonfig 升到与该基线配套的 0.2.5。

## 决策

1. **版本号 0.8.2 → 0.9.0**：`moon.mod` 与 `src/cli/cli.mbt` 的 `moonfmi_version` 同步（根包版本锁测试保证两者一致）。JSON 契约不变（仍是 `/v1`），公开 API 没删东西，按版本政策（新增功能走 minor）就是 0.9.0。
   - **为什么不是 1.0.0**：mooncakes 拒绝主版本大于 0 的包——`moon publish --dry-run` 返回 `403 Forbidden: Publishing versions with a major version greater than 0 is not enabled.`。MoonBit 官方文档写明了原因：*"Publishing version 1.0.0 or later is not supported before MoonBit 1.0."* 这个闸门跟的是 **MoonBit 1.0 正式版**，不是本模块；本机工具链还是 `1.0.0-rc1`（发布候选版），所以 `1.0.0` 现在根本发不出去。
   - 因此"升级到 1.0"落在**工具链/API 层面**（下面第 2 条），模块版本取注册表当前允许的最大一档 0.9.0；`1.0.0` 保留为闸门打开后的计划版本，roadmap 发布节奏表里也这么记了。
2. **工具链锁定 `1.0.0-rc1+3c0520448`**：本机跑的就是这个构建（`moon` 0.1.20261126 / `moonc v1.0.0-rc1+3c0520448`），CI 两个工作流都改成装这个版本，不再跟随 `latest`。
3. **moonfig 0.2.4 → 0.2.5**：零接口改动的升级，不引入新的传递依赖（仍只有 `moonbitlang/x@0.5.7`）。
4. **`moonbitlang/x` 留在 0.5.7**：上游最新已到 0.5.9，但 moonfig 0.2.5 的传递依赖锁在 0.5.7，本仓库只用到 `fs`/`crypto` 稳定面；升级另案评估，不夹在这次发布里。
5. **删掉"experimental"这个自我描述**：模块描述与 README 开头原来说"实验性"，1.0 里程碑的内容交付后与版本号矛盾；wasm 后端仍然是实验性的，这条在 README 的已知限制里保留。（0.9.0 按 semver 本来就没有稳定性承诺，"experimental" 已经由版本号表达过。）
6. **FMI 3 资源路径修正**：交叉检查发现 `fmi3/Resource.fmu` 的 CS 跑挂了（详见下面的探查修正），根因是 FMI 3 复用了 FMI 2 的 `file://` URI 构造。一并修掉。

## 探查修正

- **CI 注释过期**：注释里说"上游只发布 `latest`，带版本路径一律 403"——实测 `binaries/1.0.0-rc1%2B3c0520448/moonbit-{linux-x86_64,linux-aarch64,windows-x86_64}.tar.gz` 与 `cores/core-1.0.0-rc1%2B3c0520448.tar.gz` 全部 200，`1.0.0`、`1.0.0-rc1`（不带 hash）等别名仍然 403。锁定可行。
- **Windows 安装脚本的参数不是位置参数**：`powershell.ps1` 只认环境变量 `MOONBIT_INSTALL_VERSION`，而且构件是 `.zip` 不是 `.tar.gz`（Unix 脚本才是位置参数 + `.tar.gz`）。两个平台的写法因此不同。
- **工作区里 `docs/roadmap/p0-plan.md` 与 `p0-report.md` 又消失了**（与 2026-11-24 记录里的现象相同）。逐条查过：这两份文档被全仓 15 处引用（`docs/AGENTS.md` 的状态表、`roadmap.md`、`release-checklist.md`、`records/2026-11-02.md` 等），而同期改动的那两个文档（`config-layer.md`、`moonfig-gaps.md`）都认真更新了交叉链接——一个会更新链接的文档清理不会留下 15 处断链。判定为同一个未解释的消失现象，**已按上次的处置方式从 git 原样恢复**（与 HEAD 无 diff）。
- **交叉检查冒出一个新的 FAIL：`fmi3/Resource.fmu` 的 CS 跑挂了。** 报告里那一行原来是 `skip`（脚本按错误文本匹配："nothing to integrate" / "no Derivatives" / "returned no component" / …），换成 `FAIL` 说明错误形状变了，不是新问题。顺藤摸瓜查下来是**真的 bug，而且是老 bug**：

  - 本仓库的 [`docs/standards/fmi3-api.md`](../standards/fmi3-api.md) §2.3 写得很清楚：FMI 2 的 `fmuResourceLocation` 是 `file:///` URI，FMI 3 的 `resourcePath` 是 `resources/` 目录的**原生绝对路径**，且必须以文件分隔符结尾（Windows `\`，POSIX `/`）；同一节还写着"路径构造函数要按版本分流，不能复用同一份代码"。
  - 代码里恰恰没分流：`src/backend/native/fmi3.mbt` 把加载器给的原生路径原样丢给 `fmi2_resource_location()`，于是 FMI 3 收到的是 `file:///C:/…/resources/`。
  - Reference-FMU 的 `Resource` 模型在初始化时读 `resources/y.txt`，实现是**直接把文件名拼在路径后面**（Windows 与 POSIX 都是 `strncat(path, "y.txt")`，不像 FMI 2 分支那样补分隔符）。于是它去打开 `file:///C:/…/resources/y.txt` → 打不开 → `calculateValues` 返回 Error → `fmi3ExitInitializationMode` 返回 `fmi3Error`。
  - 这个错从 FMI 3 后端落地那天（`af15679`，P4）就在，只是当时错误文本落在脚本的 skip 白名单里，看起来像"这个 FMU 不支持该接口"。

  改法：新增 `fmi3_resource_location()`（Windows 转 `\` 并补 `\` 结尾，POSIX 补 `/` 结尾），`fmi3.mbt` 改用它；FMI 2 那边不动（FMI 2 的 URI 语义是对的）。新增两个回归测试：原生包里的路径构造单元测试，`tests/integration/fmi3_wbtest.mbt` 里跑 `fmi3/Resource.fmu` 的 CS 集成测试（断言 `resources/y.txt` 的首字符 `'a'` = 97 被读到 Int32 输出 `y`）。
- **规范里还有一条没做**：FMI 3 规范要求 FMU 没有 `resources/` 目录时传 `NULL`。加载器目前无条件传路径（FMI 2 同样如此）。语料里所有不带 `resources/` 的模型都不读资源路径，所以没有暴露；这条留作遗留，不夹在 1.0 里改（要动 shim 的 NULL 语义）。
