# P0：先确认这条路走得通

P0 不写任何用户能用的功能。它只回答五个问题：

1. 能不能读懂 FMU 里的说明书（`modelDescription.xml`）；
2. 能不能安全地打开 FMU 这个压缩包；
3. 能不能让 MoonBit 调用 FMU 里的 `.dll` / `.so`；
4. 能不能把必要的 C 代码顺利编进 MoonBit 的程序；
5. 能不能把 MoonBit 编译成浏览器和沙箱能跑的 WebAssembly 组件。

为什么要先问这五个问题？因为只要有一个答案是“不行”，后面导入器的设计就得改。与其写两个月代码再发现路走不通，不如用四周把边界试出来。每个问题结束时都要有结论、有能复现的证据，还要有不行的退路，不能停在“应该可以”。

范围也先锁死：只做 Windows 64 位和 Linux 64 位，只做 FMI 2.0.4 和 3.0.2，只碰 CS（联合仿真）这一条最小链路。macOS、32 位、ME（模型交换）和 SE（定时执行）都不在 P0。文中的术语如果看着陌生，可以查 [`glossary.md`](../references/glossary.md)。

---

## 四周怎么走

| 周 | 主要在做什么 | 周末应该能看到什么 |
| --- | --- | --- |
| 1 | 把仓库、自动检查、测试用的 FMU 准备好 | 一条命令能编译和测试；自动检查真能拦住错误；真实 FMU 能一键取到 |
| 2 | 读 XML、拆 ZIP、加载动态库 | 三件小事各自能跑，而且能挡住恶意文件 |
| 3 | 把 C 代码接进 MoonBit，跑通一个真实 FMU | MoonBit 里能完整走完一个 FMI 2 CS 模型的调用流程 |
| 4 | 试 WebAssembly，写总结 | 五个问题都有答案，可以安心开始 P1 |

前两周可以两个人并行：一个人做 XML，一个人做 ZIP；自动检查和测试 FMU 谁有空谁先做。第三周本机程序这条线是串行的，WebAssembly 那条线可以同时进行。

## 第一周：把项目立起来

### 先把目录建出来

按 [`architecture.md`](../design/architecture.md) §3 建 9 个包：`zip`、`xml`、`schema`、`fmi`、`backend/native`、`backend/wasm`、`sim`、`export`、`cli`。每个包里先只放一个空类型和一个测试，不写业务逻辑。

这一步看起来像形式主义，其实是为了两件事：后面的代码有明确的地方放；从第一天起就能检查“底层有没有反过来依赖上层”。比如 `schema` 只该依赖 `xml`，如果哪天它开始依赖 `fmi`，说明分层已经乱了，要立刻发现。

再写一个小脚本读每个包的配置，发现这种反向依赖就报错。

做完的标志：

- `moon check` 在本机（native）和 WebAssembly（wasm）两个目标上都通过；
- `moon info` 生成的公开接口清单（`.mbti` 文件）稳定，重复执行没有变化；
- 故意加一条反向依赖，检查脚本会报错。

### 让每次提交都自动检查

用 GitHub Actions，Windows 和 Linux 各跑一遍，检查四件事：代码格式、编译、测试、以及 WebAssembly 目标能不能编。MoonBit 的版本必须写死，用官方安装脚本带版本号，不要用“最新版”——否则今天能过、明天突然红了，却不知道是谁改坏的。

这一步的价值不在“有自动检查”，而在“它真的能拦住问题”。所以要做两次故意犯错：改一个空格但不格式化，格式检查必须红；手改一次公开接口清单，接口检查必须红。两次都红了，这套检查才可信。

同时写一份本地脚本，内容和线上完全一致，避免“我本地过了，CI 却不过”。

参考：[`cli-and-testing.md`](../design/cli-and-testing.md) §7；MoonBit 安装脚本 <https://cli.moonbitlang.com/install/unix.sh>。

### 准备真实 FMU 当测试样品

找 8 个左右真实的 FMU：FMI 2 和 3 都要有，CS 和 ME 都要有，Windows 和 Linux 的二进制都要有，至少一个带 `resources/` 目录，至少一个带输入输出。首选官方的 Reference-FMUs，FMI 2 缺的部分用 FMPy 的测试目录补。

FMU 文件本身不进 git——它们动辄几 MB，而且有各自的许可证。仓库里只放一份清单，记录每个文件从哪来、什么版本、什么许可证、校验和是多少；再写一个脚本按清单下载并核对。下载过一次就缓存起来，断网也能用。

做完的标志：新克隆仓库后一条命令就能取齐所有样品；故意改坏一个字节，脚本会拒绝；缓存完整时断网也能跑。

参考：[`links.md`](../references/links.md) §4。

### 用官方规则对照一下说明书（可选）

先把范围说清楚：**P0 不实现 XSD 校验器，也不把 XSD 接进 MoonFMI 的代码。** 我们只把官方 XSD 当成“标准答案”，在自动检查里请一个外部工具帮忙对一遍。这个工具可以是 Python 的 `lxml`，也可以是 `xmllint`，甚至是别的项目提供的命令行工具——只要它能读 XSD、能对 `modelDescription.xml` 给出通过或失败就行。

XSD 本身是什么？就是 FMI 官方为每个版本附的一份“语法规则书”：哪些元素必须有、能出现几次、顺序是什么、哪些值合法。它管不了“这个变量引用指向的变量根本不存在”这类跨字段问题，那部分我们自己写。

请外部工具对一遍，好处是能分清责任：

- 如果我们的解析器说文件有问题，而官方规则说没问题，那多半是我们的 bug；
- 反过来，如果官方规则说文件有问题，那就是这个测试样品本身坏了，不该拿它来测我们的代码。

这样一来，就不会出现“到底是解析器写错了，还是样品有问题”扯不清的情况。

如果你打算在另一个项目里实现 XSD，这里没有重叠：P0 不需要你提供一个 MoonBit 的 XSD 引擎，只需要在 CI 里能调用某个现成工具。将来那个项目做出来了，当然可以替换掉现在这个外部工具，但那是以后的事，不影响 P0 的结论。

这个外部工具自己也要防恶意文件：必须关掉外部实体解析、禁止联网，否则一个精心构造的 FMU 就能让自动检查去读服务器上的本地文件。

准备四类样品，提前写死预期结果：

| 样品 | 官方规则检查（有工具时） | 我们的程序 |
| --- | --- | --- |
| 完全合法 | 通过 | 通过 |
| 结构错误（缺必填、顺序错、枚举值非法） | 失败，并指出哪一行 | 失败，并指出哪一行 |
| 结构合法但语义有问题（比如变量引用不存在） | 通过 | 失败，并给出规则编号 |
| 恶意文件（外部实体、超大文件） | 拒绝 | 拒绝 |

第三行最能说明问题：官方规则只管语法，管不了语义。这类检查是我们自己要做的事，P1 才全面铺开，P0 只需要证明两类检查的职责是分开的。

**没有这个外部工具也不阻塞 P0。** 四类样品和预期结果照样要准备好，只是第二列先空着；等工具有了再补跑。这一项是“让判断更可信”，不是“能不能开工”。

参考：[`schemas/README.md`](../standards/schemas/README.md) §4、[`xsd-and-validation.md`](../design/xsd-and-validation.md) §6。

## 第二周：读懂 FMU 里的东西

### 选一个 XML 读取器，外面包一层安全限制

先说结论：**不自己写 XML 解析器**。MoonBit 已经有 `Milky2018/xml`——模仿 Rust 的 quick-xml，pull 模式，native / wasm / js 都能跑，每个事件都带源码位置，内部实体展开有上限，外部实体直接报错，而且跑过 W3C 的 1821 条一致性测试。这种活让别人干，我们没必要重造。

我们要做的是在它外面包一层（代码仍然放在 `xml` 包里），补上它不管的四件事：

- 解析前检查文件大小，默认上限 32 MB；
- 看到 `<!DOCTYPE>` 直接拒绝——FMI 的说明书不需要 DTD；
- 数元素嵌套深度、属性长度，超过上限就报错；
- 把它的位置信息转成我们统一的错误结构（文件、行、列）。

这样 `schema` 只需要面对一套稳定的事件接口。哪天这个库不维护了，换掉它也只影响 `xml` 这一层，不会污染整条解析链。

验收不看功能多全，只看四件事：

- 三个真实说明书能完整读出来：FMI 2 最小的、FMI 3 带数组的、FMI 3 带 terminals 引用的；
- 同样的文件在 native 和 wasm 上解析结果一致；
- 截断的文件、超深嵌套、层层膨胀的实体攻击（billion laughs）、超长属性，都能返回带行列号的错误，不崩溃、不卡死；
- 1 MB 的文件在开发机上 100 毫秒内读完。

如果评估时发现这个库满足不了上面任何一条，再考虑自己写。但那是退路，不是默认方案。

参考：[`moonbit-ecosystem.md`](../research/moonbit-ecosystem.md) §6、[`xsd-and-validation.md`](../design/xsd-and-validation.md) §2–§3；<https://github.com/moonbit-community/xml-mbt>。

### 选一个 ZIP 读取器，外面包一层安全策略

FMU 本质上就是一个 ZIP 压缩包，里面装着说明书、动态库和资源文件。第一版只做“读”，不做“写”。

和 XML 一样，先看现成的：`hustcer/fzip` 是从 fflate 移植过来的压缩库，支持 deflate 和 ZIP，Apache-2.0，今年还在更新。但它的 ZIP 部分比较年轻（2026 年 3 月才有第一个版本），所以定位是“用它解压，但安全策略必须由我们控制”。

具体分工：

- 能列出条目、拿到压缩前后大小和方法，就先用 `fzip`；
- 如果它不暴露足够的信息（比如拿不到压缩比、不能逐条限制大小），就自己解析 ZIP 的目录结构——这部分只有几百行，比写 XML 解析器简单得多；
- deflate 解压不要自己写，继续用库。

安全是重点。压缩包里可以藏很多坏东西：

- 文件路径写成 `../../etc/passwd`，解压时跑到目录外面去（路径穿越）；
- 一个几十 KB 的压缩包解压出几十 GB（压缩炸弹）；
- 条目校验和对不上，说明文件被改过；
- 目录索引被截断，读着读着就越界。

所以所有检查都要在写磁盘之前做完：拒绝绝对路径、盘符、`..`、反斜杠逃逸和符号链接；限制条目数量、单个文件大小、总解压大小和压缩比。解压到私有临时目录，失败时也要清理干净。ZIP64、加密、分卷先明确报“不支持”。

验收：

- 三个真实 FMU 解压后，每个文件的校验和与 `7z x` 的结果一致；
- 路径穿越、压缩炸弹、校验和错误、截断的压缩包全部被拒绝，错误信息能指到具体条目；
- 解压失败后临时目录没有残留。

参考：ZIP 格式说明 APPNOTE 6.3.10、[`importer.md`](../design/importer.md) §5。

### 试着加载一个动态库

用 C 写一个小库，导出四个函数：两个简单的算术函数、一个往结构体里填数据的函数、一个接收回调的函数。然后用两种方式在 MoonBit 里加载它：现成的 `tonyfettes/dl` 库，和直接声明 C 函数。

重点不是“能调用”，而是“出错时能不能查清楚”：库文件不存在、库存在但缺某个函数、依赖的库不在同一个目录、卸载之后文件能不能删掉。这些错误信息直接决定以后用户遇到 FMU 加载失败时，能不能自己看懂原因。

参考：[`moonbit-ecosystem.md`](../research/moonbit-ecosystem.md) §3；<https://github.com/moonbit-community/tonyfettes-dl>。

## 第三周：让 MoonBit 和 C 接上

### 中间加一层薄薄的 C 代码

FMI 的接口是 C 语言定的，里面有很多 MoonBit 不擅长的东西：结构体、可变参数、不同平台宽度不一样的布尔值。硬对硬地接，很容易读到错位的数据，而且错了很难查。

所以在 MoonBit 和 FMU 之间加一层很薄的 C 代码（后面叫它“C 中间层”）。MoonBit 只和这层打交道，这层再用官方头文件去对接真正的 FMU。结构体怎么摆、布尔值几字节、字符串怎么传，全在这层处理掉。

这层代码怎么编进 MoonBit 的构建，是 P0 最关键的一件事。按顺序试三条路，打通一条就停：

1. **直接把 C 文件放进包里一起编**：配置里写 `native-stub`，让 MoonBit 的原生构建顺手把 C 文件编掉。这是最干净的方式。
2. **先编成静态库再链接**：生成 `.lib` / `.a`，再用链接参数接进来。要注意头文件路径、运行库版本一致（`/MD` 和 `/MT` 不能混）、符号冲突。
3. **单独编成一个动态库**：用第二周的办法加载。能跑，但多一层边界，作为退路。

中间层只许用官方头文件，不许自己抄一份结构体定义——抄了就会和官方版本悄悄漂移。编译时加几条断言，把最容易错的尺寸钉死：FMI 2 的布尔是 4 字节，FMI 3 的布尔是 1 字节，值引用是 4 字节，回调结构体第一个字段必须是日志函数。

做完的标志：两个平台至少各有一条路能跑通；失败的方案记下具体报错；把实测结论写回 [`ffi-and-abi.md`](../design/ffi-and-abi.md) §8.1。

参考：[`ffi-and-abi.md`](../design/ffi-and-abi.md) §3、§8；MoonBit 包配置里 `native-stub` 和 `cc-link-flags` 两节。

### 接住 FMU 打出来的日志

FMI 2 的日志函数用的是 C 的可变参数（`printf` 那种写法），MoonBit 没法直接接。所以 C 中间层负责把消息格式化好、截断到 4 KB、复制实例名和类别，再转交给 MoonBit。

写一个最小的假 FMU，在初始化和每步计算时打日志，然后测这些情况：8 KB 的长消息截断后不越界；中文和 emoji 转一圈回来字节不变；连续一万条日志不漏内存；实例释放后不再收到迟到的回调。如果假 FMU 能起线程，顺便试试从 FMU 自己的线程里打日志会不会崩。

参考：[`fmi2-api.md`](../standards/fmi2-api.md) §5、[`ffi-and-abi.md`](../design/ffi-and-abi.md) §4。

### 把 C 侧的类型尺寸记下来

写一个小 C 程序，打印每种类型占几个字节、结构体每个字段在什么位置、枚举值是多少。Windows 和 Linux 各跑一遍，结果存成一个基准文件提交到仓库。以后每次自动检查都拿实际结果和它对比，不一致就报警。

为什么值得单独做这件事：FMI 2 的布尔是 4 字节的 `int`，FMI 3 的布尔是 1 字节的 `bool`。差三个字节，读数组时整个就错位了，而且症状往往很怪，不查尺寸根本想不到。

再写一个最小的 C 宿主程序：加载一个真实的 FMI 2 CS 模型，走完“实例化 → 初始化 → 步进若干次 → 结束 → 释放”，输出最终时间和几个变量的值。这份输出就是 P2 的对照答案——以后 MoonBit 写出来的结果要和它一致。

参考：[`ffi-and-abi.md`](../design/ffi-and-abi.md) §8.3、§10。

## 第四周：WebAssembly 与总结

### 试试 WebAssembly

先只做最小的目标：把 MoonBit 编译成 WebAssembly，导出一个 `add(i32, i32) -> i32`，用 `wasm-tools` 包成组件（component），再用 wasmtime 调用它。这一步必须过，否则后面免谈。

然后尽量往前推一步：试试组件模型里的资源释放，以及字符串和字节数组跨边界传递。推不动也要有明确结论——是 `wit-bindgen` 还没有 MoonBit 后端，还是需要手写一层适配代码，大概要多少工作量。

这一步允许失败，但不允许“没试”。因为它的结论直接决定 P7 是做、只做实验、还是先放着。

参考：[`wasm-strategy.md`](../design/wasm-strategy.md) §3、§8；<https://modelica.github.io/fmi-ls-wasm/main/>。

### 写总结，把决定定下来

新建 `docs/roadmap/p0-report.md`，写清楚：用了什么系统和工具版本；每个小实验跑了什么命令、结果如何、踩了什么坑；下面五个决定最后怎么定的。

然后回头改设计文档：`ffi-and-abi.md` 里留的七个问题逐条回答，`wasm-strategy.md` 里的三个 WebAssembly 目标标上状态，`backlog.md` 和 `roadmap.md` 勾掉已完成的部分。

报告不用长，但要让没参与的人照着能做一遍。

## 五件要拍板的事

| 问题 | 现在的倾向 | 什么情况下改主意 |
| --- | --- | --- |
| XML 读取器自己写还是用现成库 | 用 `Milky2018/xml`，外面包一层安全限制 | 它在 wasm 上跑不了、位置信息不够用，或者维护停摆 |
| ZIP 读取器自己写还是用现成库 | 用 `fzip` 解压，自己控制安全策略 | `fzip` 不暴露条目信息或压缩比，就自己解析目录，deflate 仍用库 |
| C 中间层怎么编进构建 | 直接放进包里一起编 | 两个平台有一端不通，退到静态库；再不行退到独立动态库 |
| WebAssembly 值不值得进 P7 | 先看最小目标能不能过 | 最小目标都过不了，或者字符串/资源传递没有可行路径 |
| 测试 FMU 要几个 | 8 个 | 上游不提供 FMI 2 的构建，缩到 4 个核心模型，P1 再扩 |

决定写进报告，同步改设计文档。口头说“可以了”不算。

## 怎么算做完了

- Windows 和 Linux 都能编译、测试、格式化，自动检查真能拦住错误；
- 测试 FMU 一条命令取齐，校验和能核对；
- 四类测试样品和预期结果写好；如果用了外部 XSD 工具，它能独立判断样品是否合法，而且自己不怕恶意文件；
- 真实的 `modelDescription.xml` 能安全读出来；
- 真实的 FMU 能安全解压；
- 动态库能加载、出错能查、能卸载；
- C 中间层有确定的编入方式，两个平台都能复现；
- FMU 打的日志能正确收到并截断；
- C 侧类型尺寸有基准，C 宿主能跑真实 FMU 并给出对照结果；
- WebAssembly 有明确的“能做 / 不能做”结论；
- `p0-report.md` 写完，五个决定全部定下。

哪一条没做到，就写进 [`risks.md`](risks.md)，并说明它卡住的是 P1 的哪一部分。

## 时间不够时先放弃什么

按这个顺序砍：

1. **先砍 WebAssembly 的后两个目标**：最小目标过了就够 P1 开工；
2. **再砍 C 宿主程序**：类型尺寸基准要保留，C 宿主可以挪到 P2 第一周；
3. **再砍日志的多线程场景**：先保证单线程日志正确；
4. **再砍外部 XSD 对照工具**：保留四类样品和预期结果，工具以后补；
5. **不能砍**：XML、ZIP、动态加载、C 中间层、自动检查、测试 FMU。

前四项是“多知道一点”，后六项是“能不能开始”。P0 的意义是后者。
